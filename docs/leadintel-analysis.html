O que se destaca positivamente

🏗 Decorator Pattern no Domínio

O uso de BrasilAPICompany wrappando DefaultCompany com decorators como FormattedCNPJ, TranslatedCNAE e HumanReadableDate é textbook Clean Architecture — raro em testes técnicos deste nível.

📐 Specification Pattern

ActiveCompanySpecification, StateSpecification, etc. com composição via .and()/.or()/.not() demonstra domínio sólido de DDD. Praticamente nenhum candidato chega nesse nível.

🧠 Shared Types Monorepo

A pasta shared/types separando DTOs, domain objects e validators é uma decisão arquitetural madura. Permite isomorfismo entre frontend e backend sem duplicação.

🎯 State Machine no Frontend

SearchState como union type ("idle" | "loading" | "success" | "error_inactive"...) é uma máquina de estados limpa. Evita o clássico anti-pattern de múltiplos booleans (isLoading + isError + isSuccess).

✅ Validação de Contato Rica

contactValidator.ts com detecção de domínio suspeito, email corporativo vs genérico, verificação de coerência nome-email — nível produto real, não exercício acadêmico.

🎨 UX Bem Pensada

CNPJInput com estados visuais, animação de score, ScoreIndicator com requestAnimationFrame, SkeletonLoader, InsightBlock com delay de animação — atenção rara a detalhes de interação.

Bugs & Riscos Identificados

Análise linha a linha. 3 bugs confirmados, 4 riscos de produção, 5 code smells prioritários.

🔴 Bugs Confirmados

Bug #1 Método calculateScore() nunca é chamado

Em CompanyService.ts existe um método private calculateScore() que refaz todo o cálculo de score — mas o método enrich() não o chama. O score é calculado inline diretamente no corpo de enrich(). O método está morto e duplicado.

// enrich() — calcula score inline (correto, é esse que roda)
const weighted = new WeightedLeadScore({...});
const score = weighted.getValue(); // ← usado aqui

// calculateScore() — duplicado, nunca chamado, tem fallback diferente (55 vs 50)
private calculateScore(company, raw): number {
  const sizeScore = SIZE_SCORES[sizeKey] ?? 55; // ← fallback diferente do método ativo (50)!
  ...
}

Fix: Extrair a lógica de score para um ScoreCalculator standalone e chamar de um único lugar.

Bug #2 Delay artificial de 800ms hardcoded

Em BrasilAPIRepository.ts:

await new Promise((r) => setTimeout(r, 800)); // ← isso não deveria existir em produção

Claramente inserido para "simular throttling" ou "parecer mais realista" durante desenvolvimento. Em produção, isso adiciona 800ms a todas as requisições, sem necessidade. Com um cache de Redis, a penalidade seria ainda mais perceptível nos hits.

Fix: Remover. Se rate limiting for necessário, implementar com um padrão correto (token bucket, semaphore).

Bug #3 SIZE_SCORES com chaves inconsistentes

O mapa SIZE_SCORES em scoreWeights.ts define as chaves "MEI", "MICRO", "DEMAIS", "PEQUENA", "MEDIO", "GRANDE". Porém a BrasilAPI retorna valores como "MICRO EMPRESA" e "EMPRESA DE PEQUENO PORTE".

// scoreWeights.ts
const SIZE_SCORES = { MICRO: 75, PEQUENA: 80 ... };

// CompanyService.ts
const sizeKey = (raw.porte || "").toUpperCase(); // "MICRO EMPRESA" — não faz match
const sizeScore = SIZE_SCORES[sizeKey] ?? 50; // cai no fallback 50 para quase todos

Ao mesmo tempo, mapSizeLabel() em CompanyService usa as chaves corretas ("MICRO EMPRESA"), mas o score usa as chaves erradas. Resultado: a vasta maioria das empresas recebe score de porte = 50 silenciosamente.

Fix: Normalizar sizeKey para fazer match ou unificar o mapeamento numa única estrutura.

🟡 Riscos de Produção

Risco #1 Campo raw exposto na resposta

O DTO CompanyResponseDTO inclui raw?: any, e o service faz return { ..., raw }. Isso vaza para o frontend todos os dados brutos da BrasilAPI, incluindo informações que talvez não devessem ser públicas. Em modo "developer" o frontend exibe um JSON.stringify(data) completo incluindo o raw.

Fix: Remover raw do DTO e do retorno do service em produção. Se necessário para debug, criar um endpoint separado autenticado.

Risco #2 Ausência total de rate limiting

Qualquer requisição para POST /api/company/enrich dispara uma chamada para a BrasilAPI. Sem autenticação e sem rate limiting no backend, o endpoint está aberto para:

1) Abuso via automação (scraping em massa usando o serviço como proxy)
2) Atingir limites da BrasilAPI e derrubar o serviço para todos os usuários
3) Custo operacional crescente não controlado

Fix: Implementar rate limiting por IP (express-rate-limit) e, em SaaS, por usuário autenticado. Adicionar cache de CNPJ com TTL de 24h.

Risco #3 Timeout não cancela a conexão TCP

O AbortController com timeout de 10s está corretamente implementado, mas ao chegar nesse timeout, o erro é tratado como APIError (502). Porém o response body pode continuar sendo streamado. Em ambientes Node.js com keep-alive, conexões zumbis podem acumular.

Fix: Usar undici ou configurar keepAlive: false no fetch para garantir limpeza de conexão no timeout.

Risco #4 ValidCode lança exceção para CNAE 0

Em BrasilAPICompany, o CNAE code é construído como new ValidCode(new DefaultCode(raw.cnae_fiscal || 0)). ValidCode.getValue() verifica if (!v) throw new Error("Code empty"). Se cnae_fiscal vier da API como 0 ou null, o fallback é 0, que é falsy — a instância do BrasilAPICompany lança exceção no construtor, e o erro vira um 500 genérico sem mensagem clara para o usuário.

Fix: Usar NullCode como fallback em vez de ValidCode, ou verificar v === 0 || v === null explicitamente.

🟠 Code Smells Prioritários

Smell #1 any em pontos críticos

Os tipos any aparecem em: ICNPJRepository.findByCNPJ(): Promise<any>, BrasilAPICompany constructor(private raw: any), CompanyService.generateInsights(raw: any), e no DTO raw?: any. Isso anula completamente a segurança de tipos nesses caminhos críticos.

Fix: Criar interface BrasilAPIRawResponse com todos os campos da API tipados. Isso também revelaria o Bug #3 imediatamente.

Smell #2 Lógica de score triplicada

O cálculo de ageYears aparece literalmente copiado em 3 lugares: enrich(), calculateScore(), e generateInsights(). Qualquer mudança na fórmula precisa ser feita em 3 locais.

Smell #3 Breakdown incompleto no frontend

O objeto breakdown tem 5 dimensões (isActive, contact, companyAge, size, cnae), mas o CompanyCard só exibe 2 (companyAge e contact). As dimensões isActive, size e cnae são enviadas mas silenciosamente ignoradas.

Smell #4 CRLF em arquivos shared

Os arquivos specification/index.ts e contactValidator.ts usam terminações CRLF (\r\n) enquanto o resto do projeto usa LF. Indica inconsistência no setup do repositório (.gitattributes ausente) e pode causar problemas em CI/CD em ambientes Linux.

Smell #5 ICNPJRepository mal posicionado

A interface ICNPJRepository está definida dentro de BrasilAPIRepository.ts, junto com as classes de erro (NotFoundError, APIError). Interfaces deveriam estar em sua própria camada de abstração, não no arquivo de implementação. O service importa a interface do arquivo de repository, acoplando-se ao módulo.

Score de pesos — análise crítica

O modelo de scoring atual tem uma fragilidade conceitual: peso de 40% para isActive cria um "cliff" — empresa inativa vai direto para score ~30 independente de todos os outros fatores. Para a Letalk, que vende SaaS de comunicação, o segmento (CNAE) e o tamanho talvez sejam mais relevantes que a idade. Os pesos deveriam ser configuráveis por perfil de ICP (Ideal Customer Profile) do usuário.

Análise Frontend

O que funciona bem

Bom Custom hooks bem separados

useCNPJMask, useCNPJSearch, useViewMode — cada um com responsabilidade única, sem efeitos colaterais cruzados.

Bom Componentes domain vs UI

A separação entre components/domain/ e components/ui/ é excelente. CNPJInput, ScoreIndicator, InsightBlock são componentes de domínio ricos com lógica de apresentação relevante.

Bom ScoreIndicator com RAF

A animação de contagem usando requestAnimationFrame com easing cúbico é implementação correta e performática. Evita setInterval e tem cleanup adequado.

Bom ViewMode contextual

Três modos (simple, analytic, developer) mostram pensamento de produto. O mode developer ativado via query string ?dev=true é uma abordagem elegante para debug em produção sem expor UI desnecessária.

Problemas e melhorias

Bug CNPJInput com dupla responsabilidade de state

O componente chama tanto onChange quanto onValidCNPJ — dois callbacks com semânticas diferentes. No LeadForm, ambos chamam set("cnpj"). Isso cria updates duplos de estado para o mesmo campo.

// LeadForm.tsx — dois handlers, mesmo resultado
<CNPJInput
  onChange={set("cnpj")}         // ← chamado em todo keystroke
  onValidCNPJ={(cnpj) => set("cnpj")(cnpj)}  // ← chamado quando válido
/>

Fix: Manter apenas onValidCNPJ como API. O valor parcial não precisa subir para o formulário pai.

Smell LeadContext criado mas não utilizado

LeadContext é criado com currentLead e setCurrentLead, o LeadProvider wrappa o app, mas nenhum componente chama useLead(). O estado de lead vive em useCNPJSearch() no SearchPage. O context é infraestrutura morta.

Fix: Ou usar o context para compartilhar o resultado entre componentes (remove prop drilling), ou remover o arquivo.

Smell Breakddown mostra 2/5 dimensões

O backend calcula e retorna { isActive, contact, companyAge, size, cnae } mas o CompanyCard define:

const breakdownItems = [
  { label: "Tempo de mercado", value: data.breakdown.companyAge },
  { label: "Qualidade do contato", value: data.breakdown.contact }
  // isActive, size, cnae → ignorados
];

O usuário não vê por que a empresa tem o score que tem. Isso quebra a promessa do produto de "insights acionáveis".

Smell Validação duplicada frontend/backend

O CNPJ é validado no useCNPJMask (frontend) usando cnpjValidator.ts local, E no backend usando validateCNPJ de shared/types/domain. O frontend usa um arquivo local em services/cnpjValidator.ts em vez de importar do shared. Se a lógica divergir, haverá falsos positivos/negativos.

Fix: O frontend deve importar validateCNPJ diretamente de shared/types/domain.

Smell useViewMode sem persistência

useViewMode inicializa do query param mas não persiste mudanças. Se o usuário troca para "analytic" via UI, recarregar a página volta para "simple". Para produto, o modo deveria ser salvo em localStorage ou preferências de usuário.

Análise Backend

Tratamento de erros — avaliação

Bom Error hierarchy com classes customizadas

NotFoundError e APIError extendem Error corretamente com this.name setado. O controller faz instanceof check antes de mapear para HTTP codes. Padrão correto.

Bom AbortController com timeout

O timeout de 10s com AbortController e clearTimeout no finally é implementação correta que evita memory leaks. O erro de abort é corretamente re-thrown como APIError.

Problema catch genérico perde stack trace
// controller
catch (err: any) {
  if (err instanceof NotFoundError) {...}
  if (err instanceof APIError) {...}
  res.status(500).json({ error: "Erro interno", code: "INTERNAL_ERROR" });
  // ← err nunca é logado! Erro 500 desaparece em produção
}

Fix: Adicionar console.error(err) (ou logger estruturado) no catch do 500. Em produção, sem isso, erros inesperados são invisíveis.

Risco Sem validação de corpo de request

O controller extrai const { name, email, phone, cnpj } = req.body sem validar o shape do body. Um request com body: null ou body: "string" causa crash silencioso com desestruturação para undefined, ou pode injetar valores inesperados.

Fix: Usar zod ou joi para validação do body antes de processar:

const schema = z.object({
  cnpj: z.string().min(14),
  name: z.string().optional(),
  email: z.string().email().optional(),
  phone: z.string().optional(),
});
const parsed = schema.safeParse(req.body);
if (!parsed.success) return res.status(400).json(...);
Risco Sem logging estruturado

Todo o logging é via console.log. Em produção, não há como correlacionar requests, medir latência de chamadas externas, detectar padrões de erro, ou integrar com ferramentas de observabilidade (Datadog, Sentry, etc.).

Fix: Adicionar pino (performático, JSON-first) com request ID gerado por middleware. Logar: início de request, resultado de chamada à BrasilAPI (duração, status), erros com stack.

Risco User-Agent spoofing

O repository envia headers de browser (Mozilla/5.0 Windows NT 10.0...) para a BrasilAPI. Isso é anti-pattern para uma API pública B2B — além de frágil (a BrasilAPI pode detectar), é enganoso. Para um produto real, identificar-se corretamente é melhor prática.

'User-Agent': 'LeadIntel/1.0 (contato@leadintel.com)'

Sugestões de implementação para SaaS

// Redis cache para CNPJ — exemplo de implementação
class CachedCNPJRepository implements ICNPJRepository {
  constructor(
    private repo: ICNPJRepository,
    private cache: ICache,
    private ttl = 86400 // 24h — dados da RF não mudam com frequência
  ) {}

  async findByCNPJ(cnpj: string): Promise<BrasilAPIRawResponse> {
    const cached = await this.cache.get(`cnpj:${cnpj}`);
    if (cached) return JSON.parse(cached);

    const data = await this.repo.findByCNPJ(cnpj);
    await this.cache.set(`cnpj:${cnpj}`, JSON.stringify(data), this.ttl);
    return data;
  }
}

// routes/index.ts — composição com cache
const redis = new RedisCache(process.env.REDIS_URL);
const baseRepo = new BrasilAPIRepository();
const repo = new CachedCNPJRepository(baseRepo, redis);
const service = new CompanyService(repo);

Roadmap de Melhorias

Curto prazo — 1 a 2 semanas
Correções críticas e quick wins
1. Remover o delay de 800ms

Uma linha. Impacto imediato de 800ms de latência eliminados. Bug #2

2. Tipar BrasilAPIRawResponse

Criar interface para o retorno da BrasilAPI. Vai revelar automaticamente o Bug #3 de chaves de SIZE_SCORES e eliminar os any críticos.

3. Remover calculateScore() duplicado

Extrair para ScoreCalculator separado. Remove dead code e consolida a lógica em um lugar.

4. Remover raw do DTO/response

Não expor dados internos da API no response HTTP. Segurança básica.

5. Exibir breakdown completo no frontend

Mostrar as 5 dimensões no CompanyCard. 10 linhas de código, melhora muito a transparência do score para o usuário.

6. Adicionar logging no catch de 500

console.error(err) no catch genérico do controller. Sem isso, erros de produção são invisíveis.

Médio prazo — 1 a 2 meses
Produto funcional e escalável
7. Cache de CNPJs com Redis/Upstash

TTL de 24h. Latência cai de ~1.5s para ~50ms nos hits. Essencial para qualquer volume de uso.

8. Autenticação JWT + multitenancy

Fundação do SaaS. Sem isso não há billing, cotas, histórico por usuário ou personalização.

9. Persistência de leads consultados

PostgreSQL com tabela de consultas por usuário. Histórico, ranking dos leads mais quentes, re-consulta sem custo.

10. Rate limiting por usuário

express-rate-limit por IP e por token JWT. Cotas por plano. Previne abuso e cria pressão de upgrade.

11. Testes unitários do domínio

O domínio rico (value objects, decorators, specifications) é facilmente testável. Cobrir validateCNPJ, WeightedLeadScore, contactValidator, ScoreCalculator. Vitest + cobertura >80%.

12. Validação de body com Zod

Schema validation no controller. Retorna erros descritivos em vez de crashes.

Longo prazo — 3 a 6 meses
Produto diferenciado e escalável
13. ICP Score configurável por usuário

Interface para configurar pesos e filtros do score. Transforma o produto de genérico para personalizado — e justifica ticket mais alto.

14. Segunda fonte de dados (ReceitaWS)

Fallback automático quando BrasilAPI falha. Dados complementares como quadro societário completo. Aumenta resiliência e profundidade.

15. Extensão Chrome

Enriquecimento inline no LinkedIn. Principal canal de distribuição viral B2B. Requer autenticação via extension + backend de sync.

16. Upload em lote + processamento assíncrono

CSV upload → fila (BullMQ + Redis) → webhook/email quando pronto. Abre segmento de marketing operations e operações de prospecção em escala.

17. API pública + documentação Swagger

Permitir que clientes integrem o enriquecimento em seus próprios sistemas. Abre canal de revenue via API usage + churn muito menor (embedded).

Conclusão: Este é um projeto genuinamente acima da média para um teste técnico. O uso de Decorator Pattern, Specification Pattern, domain objects ricos e uma UI com atenção a detalhes de interação demonstra maturidade. Os gaps existem principalmente em segurança, testabilidade e alguns bugs silenciosos — não em arquitetura fundamentalmente errada. Com as correções de curto prazo e a evolução de médio prazo, esta base já suportaria um produto SaaS funcional.
